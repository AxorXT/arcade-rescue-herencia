01 / Contexto

Historia y contexto

Todo estudio independiente tiene una historia de origen. La de este empieza en un foro, con un mensaje de tres líneas: “Vendo proyecto de Snake en C++, casi terminado. Funciona en mi máquina. Acepto ofertas.” La oferta fue aceptada. El “casi” resultó ser generoso.

El juego existe. Se puede compilar —a veces—, abre una ventana y permite mover una serpiente. Lo que no existe es todo lo demás: nadie sabe cuál es la versión buena, no hay pipeline, el Dockerfile se escribió a las 3 de la mañana y su autor ya no contesta. El README promete cosas que el código no cumple, y el historial de Git tiene exactamente dos commits: uno llamado first y otro llamado fix.

Ustedes entran como equipo de rescate. No como artistas: como ingenieros. La consigna del estudio es brutal y honesta: el juego puede seguir siendo feo, pero tiene que compilar, probarse y distribuirse solo.

En 210 minutos van a convertir un repositorio que da miedo en un release que da orgullo. O, al menos, en un release. Ambas cosas cuentan.

Reporte de QA · resumen ejecutivo

“No es la máquina, es el repo”

El área de calidad reporta comportamientos inconsistentes: el puntaje no siempre cuadra, el juego se cierra solo en ciertas partidas y el build del contenedor no termina. Nadie ha podido reproducirlos dos veces seguidas en la misma máquina. Ese es, precisamente, el problema.

  • Sin CI
  • Sin tests
  • Sin release

Inventario

Lo que heredaste

  • Código C++ que compila a veces y en algunas máquinas.
  • Un Dockerfile místico, sin documentación ni dueño disponible.
  • Assets, sonidos y una idea de juego que ya funciona a medias.
  • Un README optimista y un historial de Git que no explica nada.

Huecos

Lo que no existe

  • Integración continua: ni un workflow, ni un check, ni una alerta.
  • Pruebas automatizadas que alguien pueda ejecutar sin mirar el código.
  • Versiones publicadas, binarios descargables ni imagen de contenedor.
  • Documentación de instalación que sobreviva a otra persona.

Encargo

Lo que se espera de ti

  • Un pipeline reproducible que falle cuando deba fallar.
  • Un release v1.0.0 con binarios para Linux y Windows.
  • Una imagen en GHCR y una página pública en GitHub Pages.
  • Una investigación demostrable sobre una herramienta nueva.

02 / Resultados de aprendizaje

Objetivos de aprendizaje

Al terminar la sesión, cada integrante debe poder señalar una evidencia concreta —un run, un artefacto, una URL— para cada uno de estos objetivos. Si no hay evidencia, no cuenta.

  1. 01

    Diagnosticar y reparar código heredado

    Reproducir síntomas reportados, aislar condiciones y corregir la causa sin reescribir el juego completo.

  2. 02

    Diseñar un pipeline de CI funcional

    Construir un workflow que ejecute lint, pruebas y compilación en cada push y pull request, y que falle cuando el código está roto.

  3. 03

    Usar matrix strategy para multiplataforma

    Ejecutar el mismo trabajo en Linux y Windows, entendiendo qué cambia (compilador, rutas, binarios) y qué no.

  4. 04

    Publicar artifacts y releases

    Producir artefactos descargables desde una ejecución y adjuntarlos a un release etiquetado con SemVer.

  5. 05

    Construir y publicar una imagen en GHCR

    Escribir o reparar un Dockerfile de build/smoke test, autenticarse con el token del repositorio y publicar la imagen.

  6. 06

    Publicar documentación en GitHub Pages

    Convertir el README en un sitio público con instrucciones, enlaces de descarga y créditos.

  7. 07

    Operar un runner self-hosted (exploratorio)

    Entender la diferencia entre runner alojado y runner propio, y si el tiempo alcanza, registrar uno en el repositorio.

  8. 08

    Investigar una herramienta no vista en clase

    Seleccionar, implementar y demostrar una herramienta del ecosistema que no se haya cubierto en el curso.

03 / El encargo

La misión

Rescatar arcade-rescue-starter, dejarlo compilando en Linux y Windows, cubrirlo con pruebas, automatizar su construcción y distribución, y publicar un release v1.0.0 que cualquier persona pueda descargar sin hablar con ustedes.

El juego debe seguir siendo jugable. No se evalúa que sea divertido, se evalúa que sea entregable. El repositorio final se llama arcade-rescue y vive en su organización de GitHub: https://github.com/TU-ORGANIZACION/arcade-rescue.

Definición de terminado

Estos ocho puntos son la definición operativa de “terminado”. No son sugerencias: si falta uno, la entrega se considera incompleta y la rúbrica lo refleja.

  • [ ]Build limpio en Linux y Windows, sin errores y con advertencias justificadas.
  • [ ]Lint configurado y ejecutándose dentro del pipeline, no solo en tu máquina.
  • [ ]Al menos 3 pruebas automatizadas; una de ellas debe fallar con el código heredado.
  • [ ]Artifacts descargables desde al menos una ejecución de GitHub Actions.
  • [ ]Release etiquetada v1.0.0 con binarios adjuntos y notas legibles.
  • [ ]Imagen Docker publicada en GHCR y visible desde el paquete del repositorio.
  • [ ]Página de GitHub Pages publicada, con instrucciones y enlaces que funcionan.
  • [ ]Demo de 5 minutos + preguntas, ensayada, sin buscar archivos en vivo.

Nota honesta: una captura de tu terminal local no demuestra nada. La evidencia vive en GitHub: runs, artifacts, releases, paquetes y URLs públicas.

04 / Mapa del terreno

Cómo está organizado el repositorio

El starter ya trae una estructura razonable. Lo que falta no son carpetas: es el proceso que las conecta. Este es el mapa, sin pistas sobre dónde duele.

Te entregan · arcade-rescue-starter

solo lectura conceptual 
arcade-rescue-starter/
├─ CMakeLists.txt        # configuración de build
├─ Dockerfile            # heredado, sin documentar
├─ README.md             # promete más de lo que cumple
├─ assets/               # sprites, sonidos, tipografías
├─ include/              # cabeceras del juego
├─ src/                  # lógica y punto de entrada
└─ tests/                # carpeta de pruebas, casi vacía

Deben construir · arcade-rescue

ustedes lo crean 
arcade-rescue/
├─ .github/workflows/     # ci, release y pages (los escriben ustedes)
├─ docs/                  # sitio de Pages + investigacion.md
├─ CMakeLists.txt        # ajustado si hace falta
├─ Dockerfile            # reparado y documentado
├─ README.md             # instrucciones reales + badges
├─ assets/  include/  src/
├─ tests/                # al menos 3 pruebas útiles
└─ .gitignore            # build/, binarios, secretos

Reglas del mapa

  • No renombren carpetas para “ordenar”: primero entiendan por qué están así.
  • Todo lo que genera el build vive fuera del control de versiones.
  • Los workflows se escriben a mano. Un template copiado sin entenderlo se nota en la demo.
  • Si agregan documentación, que sea para otra persona, no para el profesor.

Consola: lo que reporta QA

Salida simulada de una sesión de control de calidad. Léanla como síntomas, no como diagnóstico: la causa no está escrita en ninguna parte.

qa-terminal — arcade-rescue-starter 
student@arcade:~$ ./arcade-rescue --qa
[ OK ] ventana 1280x720 creada
[ OK ] entrada de teclado detectada
[WARN] el puntaje no coincide con lo que muestra el HUD
[FAIL] el juego se cierra solo tras cierta secuencia de movimientos
[FAIL] el build del contenedor se detiene sin mensaje claro
[ .. ] 2 de 5 comprobaciones superadas
student@arcade:~$ echo "no es la máquina, es el repo"
no es la máquina, es el repo
student@arcade:~$ # TODO: reproduzcan cada síntoma antes de tocar código

Criterio de lectura: si no pueden reproducir un síntoma, no lo “arreglen”. Primero anoten en qué condiciones aparece. Un bug que no se reproduce sigue siendo un bug, solo que con peor documentación.

06 / Manual de operaciones

Instrucciones por etapas

Ocho bloques desplegables con pasos accionables, comandos genéricos y un criterio de éxito que se puede observar. Las pistas de GitHub Actions son eso: pistas. El YAML completo lo escriben ustedes.

Convención: TU-ORGANIZACION es su organización o usuario. Los comandos son ejemplos seguros; adáptenlos a su entorno antes de ejecutarlos.

01 Reconocimiento del proyecto 15 min +

Objetivo: entender qué se heredó y dejar el repositorio remoto listo, sin modificar nada del código todavía.

  1. Descarguen o clonen el starter y ábranlo en el editor del equipo.
  2. Lean el README.md completo. Subrayen cada promesa que el código no cumple.
  3. Compilen tal como está y guarden la salida completa (no solo la última línea).
  4. Ejecuten lo que exista en tests/ y anoten el resultado real.
  5. Prueben el Dockerfile heredado. Si falla, guarden el error íntegro.
  6. Creen el repositorio remoto y suban el estado inicial sin retoques.
git init
git add .
git commit -m "chore: estado inicial del proyecto heredado"
git branch -M main
git remote add origin https://github.com/TU-ORGANIZACION/arcade-rescue.git
git push -u origin main
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure

Higiene mínima Creen un .gitignore con build/ y los binarios generados antes del primer commit. Un repositorio con basura compilada encima es un museo, no un proyecto.

✓Criterio de éxito: el repo remoto refleja el estado inicial y existe una lista escrita de síntomas priorizados, con pasos para reproducir cada uno.

02 Game Rescue 40 min +

Objetivo: que el juego deje de comportarse mal, con correcciones trazables y sin reescribirlo.

  1. Reproduzcan cada síntoma en orden de impacto: primero lo que impide jugar.
  2. Repartan lectura de código, reproducción y documentación. Nadie hace las tres a la vez.
  3. Corrijan de a un problema por commit, con mensaje fix: y una línea de contexto.
  4. Si un síntoma no se reproduce, registren las condiciones exactas y sigan con el siguiente.
  5. Recompilen desde cero (borren build/) antes de declarar victoria.
git switch -c fix/rescate
# ... corrección y verificación ...
git add .
git commit -m "fix: corrige el sintoma reportado por QA"
git push -u origin fix/rescate

Criterio de revisión Abran un pull request, aunque trabajen solos. El PR es la evidencia de que saben trabajar con ramas, y es el lugar natural donde el pipeline va a correr más adelante.

✓Criterio de éxito: los síntomas reportados ya no se reproducen y cada corrección tiene su commit identificable. El juego sigue siendo feo; eso no es un bug.

03 Testing y lint 30 min +

Objetivo: demostrar que los bugs quedaron corregidos y que el estilo no depende del criterio de cada quien.

  1. Elijan un framework de pruebas compatible con CMake y C++17; si usan uno simple, justifíquenlo.
  2. Escriban al menos 3 pruebas: una debe fallar con el código heredado y pasar con la corrección.
  3. Conserven la evidencia del rojo: captura del run, commit o rama donde la prueba falla.
  4. Configuren clang-format con un archivo de configuración en la raíz del repo.
  5. Si clang-tidy es viable, actívenlo; si no, documenten la alternativa y el motivo.
  6. Ejecuten todo en local hasta que quede en verde sin trampas.
ctest --test-dir build --output-on-failure
# ejemplo de formato, ajusten a sus archivos
clang-format --dry-run --Werror src/*.cpp include/*.h

Regla dura No modifiquen la prueba para que pase ni alteren el código solo para complacer al linter. Un test que valida el bug no es un test: es un monumento.

✓Criterio de éxito: 3 pruebas mínimas pasando, lint sin errores y evidencia clara de que al menos una prueba detectaba el comportamiento heredado.

04 CI/CD y matrix 35 min +

Objetivo: que GitHub haga, en cada push y cada PR, lo que hasta ahora hacían a mano.

  1. Creen el primer workflow con un solo job y un solo sistema operativo.
  2. Disparen en push y pull_request; el PR debe mostrar checks.
  3. Separen (o nombren claramente) lint, test y build dentro del flujo.
  4. Cuando el job básico esté verde, añadan la matrix Linux/Windows.
  5. Provóquenlo: suban una rama con un error deliberado y comprueben que el check falla. Después reviertan.
  6. Si es posible, exijan el check para fusionar a main.
# .github/workflows/ci.yml — esqueleto incompleto
name: CI
on: [push, pull_request]
jobs:
  build:
    runs-on: ${{ matrix.os }}   # TODO: define la matriz
    # TODO: checkout, dependencias, configurar, compilar, probar

Qué investigar en el Marketplace actions/checkout, actions/cache, actions/upload-artifact y las acciones de configuración de compilador que necesite su stack. Lean sus entradas antes de copiarlas.

✓Criterio de éxito: un PR muestra checks verdes y una rama con código roto genera un run rojo. Si todo está siempre verde, aún no han probado nada.

05 Artifacts y releases 25 min +

Objetivo: que el resultado del pipeline sea descargable por alguien que no estuvo en la clase.

  1. Suban los binarios generados como artifact, con un nombre que distinga la plataforma.
  2. Si el artifact puede salir vacío, hagan que el paso falle en ese caso.
  3. Descarguen el artifact desde la interfaz y ejecuten el binario en una máquina distinta.
  4. Cuando esté validado, creen un tag anotado v1.0.0 y súbanlo con tags.
  5. Añadan un workflow que, al publicarse el tag, adjunte los binarios a la release.
  6. Escriban notas de release legibles: qué cambió, qué se arregló, cómo se instala.
# fragmento incompleto — complétenlo
      - uses: actions/upload-artifact@v4
        with:
          name: arcade-${{ matrix.os }}
          path: build/              # TODO: apunten a la salida real
          if-no-files-found: error
git tag -a v1.0.0 -m "Primera versión rescatada"
git push origin main --tags

Diferencia clave Un artifact caduca y vive dentro de un run. Un release es público, permanente y tiene URL propia. No son sinónimos y la rúbrica los evalúa por separado.

✓Criterio de éxito: existe una release v1.0.0 con al menos un binario descargable por plataforma y notas que una persona externa puede seguir.

06 Docker y GHCR 25 min +

Objetivo: construir una imagen reproducible que compile y haga un smoke test sin entorno gráfico.

  1. Lean el Dockerfile heredado y anoten qué intenta hacer antes de cambiarlo.
  2. Ajusten el alcance: build y prueba headless dentro del contenedor; la GUI no va aquí.
  3. Construyan la imagen localmente y ejecuten el smoke test.
  4. Autentíquense en GHCR con un token de alcance mínimo y publiquen la imagen.
  5. Automaticen build y push desde el workflow usando el token del repositorio.
  6. Verifiquen que el paquete es visible y que un docker pull funciona.
docker build -t ghcr.io/TU-ORGANIZACION/arcade-rescue:v1.0.0 .
docker run --rm ghcr.io/TU-ORGANIZACION/arcade-rescue:v1.0.0
docker push ghcr.io/TU-ORGANIZACION/arcade-rescue:v1.0.0

Pista Actions docker/login-action y docker/build-push-action. Para publicar en GHCR hace falta permiso de escritura de paquetes; declárenlo en el workflow, no en un archivo de texto.

✓Criterio de éxito: la imagen aparece en GHCR asociada al repositorio, se puede descargar y el smoke test termina con código de salida 0.

07 GitHub Pages 15 min +

Objetivo: publicar una página que explique el juego y lleve a las descargas reales.

  1. Decidan la fuente de publicación: carpeta docs/ en main, rama dedicada o deploy por Actions.
  2. Escriban el contenido mínimo: qué es, cómo se juega, cómo se compila, dónde se descarga.
  3. Incluyan enlaces al repositorio, al release y al paquete de GHCR.
  4. Activen Pages en la configuración del repositorio y esperen la publicación.
  5. Abran la URL en una ventana privada y prueben todos los enlaces.

Pista Actions Si publican desde un workflow, investiguen actions/configure-pages, actions/upload-pages-artifact y actions/deploy-pages. Si publican desde una carpeta, no necesitan workflow: necesitan contenido.

✓Criterio de éxito: la URL pública carga sin autenticación, se entiende qué es el proyecto y ningún enlace termina en una página de error.

08 Demo y evaluación 25 min +

Objetivo: defender el trabajo en 5 minutos, con evidencia y sin improvisar.

  1. Ensayo cronometrado completo, al menos una vez, con el mismo orden que usarán en la demo.
  2. Dejen abiertas las pestañas: repo, run verde, run rojo, release, GHCR, Pages e investigación.
  3. Repartan la palabra: contexto, bugs, pipeline, distribución, cierre.
  4. Preparen respuesta para tres preguntas probables del profesor.
  5. Reserven dos minutos de margen. Siempre aparece algo que no carga.

Regla de oro El que habla no navega. Si necesitan buscar un archivo durante la demo, la demo ya perdió 30 segundos y algo de credibilidad.

✓Criterio de éxito: la demo termina dentro del tiempo, cada afirmación tiene una URL o un run que la respalda y el equipo puede explicar por qué tomó cada decisión.

07 / Restricciones técnicas

Requisitos técnicos

No son caprichos: cada requisito existe para que el resultado se pueda reproducir en otra máquina. Si algo no aplica a su caso, se justifica por escrito en el README.

Stack mínimo aceptado
ComponenteRequisitoNotas
LenguajeC++17El código heredado ya lo usa; no migren de versión a mitad del rescate.
BuildCMake ≥ 3.20Configuración fuera del árbol de fuentes (-S . -B build).
Frontend gráficoraylibSi usan otra biblioteca, debe estar justificada y seguir siendo multiplataforma.
DependenciasSin paquetes exóticosTodo debe instalarse desde un gestor estándar o vendorizarse en el repo.
PlataformasLinux y WindowsAmbas compilan y pasan pruebas en CI. “En mi Mac funciona” no es una plataforma de entrega.
ContenedorSolo build y smoke test headlessLa imagen no abre ventanas ni requiere GPU. Si el juego necesita pantalla, no va en el contenedor.
VersionadoSemVer, tag v1.0.0Tag anotado, no un tag ligero perdido en el historial.

Lint

  • clang-format obligatorio, con configuración versionada.
  • clang-tidy recomendado; si no es viable, alternativa justificada.
  • El lint corre en CI, no solo en la máquina de quien lo configuró.
  • Reglas nuevas se discuten en el PR, no se desactivan en silencio.

Testing

  • Mínimo 3 pruebas automatizadas ejecutables con ctest.
  • Al menos una debe fallar con el código heredado y pasar tras la corrección.
  • Pruebas deterministas: sin red, sin GUI, sin depender del reloj.
  • Nombres descriptivos; “test1” no explica qué protege.

Artifacts, releases y contenedor

  • Artifacts: nombre por plataforma, retención razonable, error si la carpeta sale vacía.
  • Release: notas escritas por humanos, binarios adjuntos y enlace a la imagen.
  • GHCR: imagen etiquetada con la versión; el paquete debe ser visible desde el repo.
  • Secretos: únicamente tokens del repositorio o secretos configurados; nunca en el código.
  • Reproducibilidad: desde un clon limpio, los comandos del README deben bastar.

09 / Opcional

Retos adicionales

No son obligatorios y no compensan un pipeline roto. Si el núcleo está sólido y sobra tiempo, el conjunto de retos suma como máximo +10 puntos en la rúbrica de demo (o insignias del curso). Los valores por tarjeta son orientativos y el total se topa en +10. Elijan pocos y háganlos bien.

Runner self-hosted

Registren una máquina propia y ejecuten al menos un job ahí. Documenten requisitos y qué pasa si se apaga.

  • +2
  • infra

Cobertura de pruebas

Midán cobertura con una herramienta del stack y publiquen el reporte como artifact o badge.

  • +2
  • calidad

Cache de dependencias

Aceleren el pipeline con caché correctamente invalidada. Demuestren la diferencia de tiempo entre runs.

  • +1
  • performance

Sanitizers

Compilen con AddressSanitizer o UndefinedBehaviorSanitizer y ejecuten las pruebas bajo esa configuración.

  • +2
  • calidad

Docker multi-stage

Separen build y runtime en etapas distintas y justifiquen el tamaño final de la imagen.

  • +1
  • docker

Dependabot

Activen actualizaciones automáticas y muestren un PR generado, revisado y fusionado.

  • +1
  • mantenimiento

Release notes automáticas

Generen las notas desde el historial o desde PRs etiquetados. Editen el resultado antes de publicarlo.

  • +1
  • release

Firma de artifacts

Firmen los binarios o la imagen y verifiquen la firma en otro entorno. Expliquen por qué importa.

  • +2
  • seguridad

Y uno de cierre: deploy de Pages disparado desde un tag, no desde cada push a main. Vale +1 y demuestra que entienden la diferencia entre integrar y publicar.

10 / Fuera del aula

Investigación obligatoria

Elijan una herramienta que no se haya visto en clase, impleméntenla en el proyecto y demuestren que funciona. No alcanza con describirla: tiene que aparecer en el pipeline, en el repositorio o en el release.

Qué se evalúa

  • Que la herramienta sea realmente nueva para el equipo.
  • Que resuelva un problema concreto del proyecto.
  • Que exista una implementación demostrable, no un resumen de blog.
  • Que puedan explicar límites, costos y alternativas.

Cómo se entrega

  • Archivo docs/investigacion.md en el repositorio.
  • Respuesta a las 7 preguntas de la plantilla.
  • Enlace a la evidencia: run, artifact, captura o commit.
  • Un minuto de la demo para explicarlo en vivo.
Ocho opciones válidas (pueden proponer otra)
Herramienta Qué es Problema que resuelve Dificultad Evidencia esperada

Plantilla para docs/investigacion.md

Respondan las siete preguntas en orden. Respuestas concretas, sin relleno.

# Investigación: <nombre de la herramienta>

## 1. ¿Qué es y qué problema resuelve?
## 2. ¿Por qué la elegimos frente a otras alternativas?
## 3. ¿Cómo se integra en nuestro pipeline o repositorio?
## 4. ¿Qué configuración mínima necesitó?
## 5. ¿Qué evidencia demuestra que funciona? (URL, run, captura)
## 6. ¿Qué limitaciones, costos o riesgos tiene?
## 7. ¿Qué aprendimos y qué haríamos distinto?

Advertencia: “lo vi en un video” no es una respuesta. Si no pueden mostrar la herramienta corriendo en su proyecto, la investigación no cuenta.

12 / Convivencia técnica

Reglas de trabajo

Un release se construye en equipo, pero se rompe por una sola persona que hace lo que no debe. Estas reglas existen para que el fracaso, si ocurre, sea colectivo y honesto.

Equipos de 3 a 4

Roles definidos desde el minuto uno. Un equipo sin dueño de release es un equipo que no publica.

IA permitida, con declaración

Pueden usarla para dudas, código y redacción. Declaren qué usaron en el README o en la demo; si no pueden explicarlo, no cuenta.

Secretos fuera del repositorio

Prohibido hardcodear tokens, contraseñas o claves. Usen secretos de GitHub o el token del repositorio.

Nada de build/ versionado

Binarios, objetos y carpetas generadas no se commitean. El .gitignore se crea antes del primer commit, no después del incidente.

No maquillar pruebas

Prohibido modificar el código para “hacer pasar” un test sin corregir la causa. Si la prueba está mal escrita, se corrige la prueba y se explica.

Commits significativos

Un commit, una intención. “cambios”, “fix”, “ahora sí” no describen nada y la rúbrica de Git lo nota.

Respeto al tiempo

Si se atascan más de 10 minutos, pidan pista o roten roles. El silencio consume el bloque entero y contagia al resto.

Integridad académica

No se copia el pipeline de otro equipo ni se presenta como propio. Compartir conocimiento sí; compartir el YAML completo, no.

Consecuencia práctica: un secreto filtrado o un historial fabricado anulan los criterios de Git y CI aunque el resto del trabajo esté impecable. No vale la pena.

13 / Defensa

Criterios de demostración

Cinco minutos por equipo, cronometrados. No se trata de mostrar todo: se trata de demostrar que entienden lo que construyeron. La evidencia se abre antes de empezar; durante la demo solo se explica.

Guion sugerido · 8:00

  • 0:00 – 0:30Contexto: qué recibieron, qué decidieron rescatar y en qué orden.
  • 0:30 – 2:30Un bug concreto: síntoma, reproducción, corrección y prueba que lo cubre.
  • 2:30 – 4:30El pipeline: jobs, matrix, qué pasa cuando algo falla. Muestren un run rojo real.
  • 4:30 – 5:30Artifacts y release: descarga real de un binario y notas que se entiendan.
  • 5:30 – 6:30Docker y GHCR: imagen publicada, smoke test y por qué no corre GUI.
  • 6:30 – 7:30Pages e investigación: URL pública y la herramienta nueva en 60 segundos.
  • 7:30 – 8:00Cierre: qué falta, qué aprendieron, qué harían distinto.

Señales de alarma

  • Pipeline verde sin pruebas reales. El YAML corre, pero no valida nada.
  • Artifacts vacíos. El paso sube una carpeta que no existe o no contiene el binario.
  • Imagen solo local. Nunca se publicó; el paquete de GHCR no existe.
  • Nadie sabe qué hace un job. Se copió sin leer y ahora nadie puede defenderlo.
  • Demo que busca archivos en vivo. Señal de que no hubo ensayo.

Lo que preguntará el profesor

  1. ¿Por qué esa prueba y no otra? ¿Qué bug atrapa exactamente?
  2. Muéstrame un run rojo. ¿Por qué falló y cómo lo arreglaron?
  3. ¿Qué pasa si mañana cambia la versión de una dependencia?
  4. ¿Dónde vive el token que usa el pipeline y por qué no está en el repo?
  5. ¿Qué diferencia hay entre un artifact y un release?
  6. ¿Por qué la imagen no ejecuta la interfaz gráfica?
  7. Si el runner de Windows se cae, ¿qué se pierde y qué sigue funcionando?

Qué debe estar abierto antes de empezar

  • Repositorio con la pestaña de Actions filtrada por runs verdes y rojos.
  • Release v1.0.0 y su archivo descargable.
  • Paquete de GHCR visible desde el repositorio.
  • Sitio de Pages en una pestaña aparte.
  • docs/investigacion.md renderizado.
  • Una terminal lista, sin comandos escritos de antemano.

Sobre las pistas: pedir ayuda tiene un costo en la rúbrica de demo; ocultarlo cuesta más. Si la usaron, díganlo y expliquen qué aprendieron de ella.

14 / Dudas razonables

Preguntas frecuentes

Las que siempre aparecen, respondidas antes de que las pregunten.

¿Puedo usar otro lenguaje que no sea C++?

No. El proyecto heredado está en C++17 y la actividad trata sobre rescatar ese código, no sobre elegir stack. Migrar el lenguaje consume el tiempo de todo el equipo y no suma en ninguna rúbrica.

¿raylib es obligatoria?

Es el frontend gráfico sugerido y el que ya trae el starter. Si usan otra biblioteca, debe ser multiplataforma, instalarse sin pasos exóticos y estar justificada en el README. Cambiarla sin motivo es tiempo perdido.

¿Y si no tengo Docker instalado?

Pueden construir la imagen desde el runner de CI, que sí lo tiene. Si tampoco es posible, documenten la limitación y demuestren el resto del flujo; la rúbrica de Docker y GHCR se ve afectada, no anulada.

¿Cuántos workflows necesito como mínimo?

Tres responsabilidades: integración continua, release/publicación y página. Pueden vivir en dos archivos si está bien separado, pero un solo workflow gigante que hace todo es difícil de defender en la demo y de mantener después.

¿Puedo usar un template de workflow de internet?

No para los workflows. Pueden leer documentación y ejemplos, pero el YAML final debe ser escrito y entendido por el equipo. Si no pueden explicar un job línea por línea, no debería estar ahí.

¿Qué pasa si el runner self-hosted falla?

Es un reto opcional: si falla, se documenta y se sigue con los runners alojados. Un reto roto no debe arrastrar el pipeline principal. La regla es simple: lo obligatorio primero, lo experimental después.

¿Cómo evidencio lo que hice?

Con URLs y logs: enlace al run, al artifact, a la release, al paquete de GHCR y a Pages. Las capturas sirven como apoyo, no como prueba principal. Si la evidencia no es accesible para el profesor, no existe.

¿Qué pasa si no llegamos con el tiempo?

Entregan lo que esté publicado y sean honestos en la demo. Un release incompleto pero reproducible vale más que cinco workflows a medio escribir. Prioridad: build, tests, CI, release, luego el resto.

15 / Vocabulario

Glosario mínimo

Dieciséis palabras que van a aparecer en la demo. Si no puedes explicarlas sin leer la diapositiva, todavía no son tuyas.

Pipeline

Secuencia automatizada de etapas: compilar, probar, analizar, empaquetar y publicar. Si una etapa falla, las siguientes no deberían ejecutarse.

Workflow

Archivo YAML en .github/workflows/ que declara cuándo y cómo se ejecuta un pipeline. Un repositorio puede tener varios.

Job / Step

Un job es un conjunto de pasos que corre en un runner; un step es una unidad dentro del job (un comando o una action). Los jobs pueden correr en paralelo.

Runner

Máquina que ejecuta un job. Puede ser alojada por GitHub (ubuntu-24.04, windows-2022) o propia (self-hosted).

Matrix

Estrategia que expande un job en varias combinaciones de variables, por ejemplo sistema operativo y versión de compilador.

Artifact

Archivo producido por un run y conservado para descarga. No es una release: caduca y no tiene URL pública permanente.

Release / Tag

Una release es un punto publicable asociado a un tag de Git. El tag es la referencia inmutable; la release añade binarios y notas.

SemVer

Versionado MAYOR.MENOR.PARCHE. Un cambio incompatible sube MAYOR; una funcionalidad nueva, MENOR; una corrección, PARCHE.

GHCR

GitHub Container Registry. Almacén de imágenes Docker asociado al repositorio, con permisos por paquete.

Pages

Alojamiento estático de GitHub. Publica HTML, CSS y JS; no ejecuta backend ni procesos en segundo plano.

Lint

Análisis automático de estilo y errores probables. No sustituye a las pruebas: detecta lo que el compilador tolera y el revisor humano también.

Sanitizer

Instrumentación del compilador (ASan, UBSan) que detecta accesos inválidos a memoria y comportamiento indefinido en tiempo de ejecución.

Cache

Almacenamiento reutilizable entre runs (dependencias, artefactos de compilación). Acelera el pipeline; nunca debe ser la única fuente de verdad.

Secret

Valor cifrado disponible en el workflow. Nunca se imprime ni se commitea. GITHUB_TOKEN es un secreto efímero que GitHub genera por run.

Idempotencia

Propiedad de una operación que produce el mismo resultado si se ejecuta una o varias veces. Un pipeline repetible es idempotente.

Reproducibilidad

Capacidad de obtener el mismo resultado en otra máquina, en otro momento y con otra persona. Es el criterio que separa «funciona» de «funciona aquí».

Regla mnemotécnica: si una palabra del glosario aparece en tu demo y no puedes dar un ejemplo del proyecto, bórrala de la demo.

Recursos recomendados

Documentación oficial, no tutoriales de terceros. Se lee con el proyecto abierto al lado y se contrasta con lo que hace el pipeline.

GitHub Actions

docs.github.com/actions — sintaxis de workflows, matrix, caché, artifacts y permisos.

Docker

docs.docker.com — multi-stage builds, usuario sin privilegios y buenas prácticas de imagen.

CMake

cmake.org/documentation — targets, install(), CPack y FetchContent.

CTest

ctest(1) — descubrimiento de pruebas, propiedades y salida en caso de fallo.

raylib

clang-format / clang-tidy

ClangFormat y clang-tidy — formato y análisis estático con configuración versionada.

SemVer

semver.org — reglas de versionado y por qué v1.0.0 no es lo mismo que 1.0.

Conventional Commits

conventionalcommits.org — mensajes que permiten generar notas de release sin inventarlas.
